티츄 M3 — 랜덤 매칭 · 다중 방 결과

2026-10-08 ~ 10-09 · main 머지 ca634a9(origin 푸시) · 스펙 docs/superpowers/specs/2026-10-08-mp-m3-matchmaking-design.md

결론: 서버 한 대가 랜덤 매칭으로 여러 판을 동시에 돌립니다. 테스트와 실기 확인(에디터 + S23)을 모두 통과해 main에 들어갔습니다. 남은 일은 클라우드 배포(M2b, AWS 답변 대기)와 이탈·타이머 처리(M5)입니다.

1. 무엇이 바뀌었나

플레이어가 보는 흐름

  1. 메뉴 → 온라인 대전 → 주소 입력(출시 빌드 주소 고정은 M4) → 접속
  2. 대기 화면: 상대를 찾는 중 · 2명 대기 · 18초 뒤 AI와 시작(초는 앱이 직접 줄여 셉니다)
  3. 방이 꽉 찼을 때: 서버가 붐빕니다 · 대기 순번 1 → 자리가 나면 자동 입장
  4. 방이 만들어지면 좌석이 무작위로 정해지고(사람끼리 같은 팀일 수도 상대일 수도 있음), 테이블로 들어갑니다.

폰의 첫 접속 실패("서버에 연결할 수 없습니다")는 폰이 Wi-Fi에 연결돼 있지 않아서였습니다. 앱 문제가 아닙니다.

3. 어떻게 만들었나

8개 태스크를 태스크마다 새 구현 에이전트 + 독립 리뷰로 진행했고, 마지막에 브랜치 전체 리뷰를 한 번 더 했습니다. 동시성이 걸린 대기열·방·연결 태스크는 가장 강한 모델이 리뷰했습니다.

구성 요소역할
Connection소켓 하나: 송신 큐, 수신, 크기·형식·레이트 검사. 받은 액션을 지금 소속(대기열 또는 방)에 넘김
Matchmaker대기열, 30초 충원, 방 상한, 순번 안내. 판단은 잠금 하나 안에서(묶인 연결은 같은 순간 방 소속으로 바뀜)
Room판 하나의 수명: 무작위 좌석, Hard AI, 매치 세션, 이탈 시 그 방만 종료

예전 단일 방 전송(WebSocketServerTransport·MatchHost·SeatTable)은 지웠습니다. 이전 판의 늦은 연결을 거르던 "세대 번호"가 필요 없어져 코드가 단순해졌습니다.

진행 중 내린 결정

결정틀렸을 때 비용
서버 1초 타이머에 예외 처리 추가(계획 밖) — 타이머 안 예외는 서버 프로세스를 죽이므로방어 코드 몇 줄
"매치가 끝난 직후의 이탈"을 폴트로 보지 않는 가드는 코드 검토로만 검증(단위 테스트로 닿지 않는 구간). 실제 흐름은 E2E가 덮음회귀가 생기면 정상 종료 뒤 "연결 끊김"이 잘못 뜰 수 있음
테스트 시계를 틱 단위로 보정(29.9초 + 0.1초가 30초에 1틱 모자람). 단언은 그대로없음
최종 수정은 문서만(운영 안내의 "판 진행 중 확인법"이 옛 로그 문구라 운영자가 진행 중인 판을 재시작할 위험)—
방 시작 실패 시 슬롯 누수 가드는 M5로 이월스레드 생성 실패 같은 드문 경우 방 자리 하나가 재시작 전까지 묶임

4. 남은 일

출시 전 반드시: 낯선 사람과 매칭되므로 M5(턴 타이머·재접속·AI 인계)가 필요합니다. 지금은 잠수한 사람이 방 하나를 끝없이 붙잡을 수 있고, 한 명이 나가면 판 전체가 끝납니다.
  • M2b 클라우드 배포: Lightsail 서울 할당량 케이스에 10/09 회신 완료(AWS가 연구용 GPU 양식을 잘못 보내 정정). 도메인 케이스는 미배정. 할당량이 풀리면 인스턴스 → 배포 → 폰 LTE 접속 확인.
  • 방 상한 실측: 배포 뒤 Lightsail에서 부하를 한 번 재서 --max-rooms 기본값을 확정합니다(버스트형 CPU라 AI가 많으면 크레딧이 떨어짐).
  • M5로 넘긴 것: 방 시작 실패 가드, 대기열 카운트다운이 동시 입·퇴장 때 드물게 어긋나는 문제(표시만), 폴트 로그가 AI 좌석까지 찍히는 잡음.
  • M4: 출시 빌드에 주소 고정, 로비 UI.
  • 출시 전 신고: 온라인 대전 추가에 따른 Data safety·등급·개인정보처리방침 재신고.
