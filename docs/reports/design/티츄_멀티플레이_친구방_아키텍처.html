친구방 멀티플레이, 권위는 어디서 돌 것인가

1차 범위는 친구방 한 종류로 확정됐다. 코드를 읽어 보니 멀티플레이용 이음새는 이미 거의 다 깔려 있고, 기획서 7장에는 전송 기술과 무관한 논리 프로토콜이 이미 확정돼 있다. 그래서 지금 필요한 결정은 사실상 하나다 — 전체 손패를 쥔 권위 세션이 플레이어 기기에서 도는가, 서버에서 도는가.

출발점

맨땅이 아니다

권위 검증 이미 있음 GameEngine.Apply — 10만 판 무결성 검증
논리 프로토콜 기획서 7장 메시지 13종 · 시야 마스킹 · 타임아웃 · 재접속

범위 밖 계정 · 랭킹 친구방은 MMR·시즌·매칭이 필요 없다

드라이버는 사람과 AI를 구분하지 않는다

AsyncGameDriver는 좌석별 IDecisionAgent에게 await로 묻는 풀(pull) 구조다. 원격 플레이어는 "네트워크에서 그 좌석의 액션이 도착할 때까지 기다리는 에이전트"면 된다. 고정 반복 순서와 오라클 동일성이 그대로 유지된다.

서버가 해야 할 검증이 이미 작성돼 있다

기획서가 요구하는 검증 4항목 — 행동권자 확인 · 손패 실재 · 합법 조합 · 특수 규칙 — 이 전부 GameEngine.Apply 안에 있고, 거부 시 상태 불변 + 이유 반환까지 같은 모양이다. 서버용 룰 코드를 새로 쓸 일이 없다.

브로드캐스트 훅도 이미 있다

RunRoundAsync(onApply:)는 매 액션 적용 직후 호출된다. 지금은 화면 갱신에 쓰이고, 멀티에서는 바로 이 자리에서 좌석별 마스킹 뷰를 내보내면 된다. 새 수명주기를 만들 필요가 없다.

한 군데만 주의가 필요하다 — 폭탄. 드라이버는 폭탄 창에서 좌석을 순회하며 각자에게 묻는데, 사람에게 이걸 물으면 매 트릭마다 전원 대기가 걸린다. 지금 앱은 그래서 인간 폭탄을 "예약 메일박스"(TakePendingBomb)로 처리한다. 원격 좌석도 같은 방식으로 일반화되고, 이는 기획서가 명시한 "동시 도착 폭탄은 수신 순서로 직렬화"와 정확히 맞아떨어진다.

전용 서버를 권하는 이유 세 가지

  • 모바일 친구방에서 호스트 모델은 제품을 깨뜨린다. 1000점 매치는 30~60분이 걸린다. 그 사이 호스트 한 명이 카톡을 확인하러 앱을 내리면 네 명의 판이 날아간다. 폰에서는 드문 사고가 아니라 기본 동작이다.
  • 호스트 모델의 결함은 벤더를 바꿔도 남는다. Photon을 Supabase Realtime으로 갈아타면 tick 모델 접합 비용과 벤더 중복은 사라지지만, "권위가 플레이어 폰에 있다"는 근본은 그대로다 — 상대 손패도 그 폰에 있고, 그 폰이 백그라운드로 가면 판이 끝난다.
  • 이 저장소는 이미 서버를 반쯤 갖고 있다. 룰·정산·AI가 유니티 타입 0 참조 순수 C#이다. 서버는 그 코드를 호스팅하는 얇은 껍데기이며, 덤으로 "끊긴 좌석을 서버의 PIMC가 인계"가 거의 공짜로 따라온다.

반대쪽 근거도 정직하게

①의 장점은 진짜다 — 운영 부담 0. 서버는 출시 후에도 계속 살아 있어야 하는 고정 부채다. 플레이어가 0명인 달에도 켜 둬야 하고, 프로토콜 버전 호환·보안 패치·장애 대응이 전부 1인분 숙제로 남는다. "그 숙제를 지고 싶지 않다"가 결론이라면 ①이 올바른 선택이고, 그때는 호스트 이탈을 제품 사양으로 수용하면 된다(방장이 나가면 판 종료 안내). 그리고 그 경우 Photon보다 Supabase 올인이 낫다 — 벤더가 하나로 줄고 계정·랭킹까지 같은 프로젝트에 들어온다.

추가 검토 · Supabase

Supabase는 어디에 맞고 어디에 안 맞는가

결론부터 — 메타 백엔드로는 훌륭하고, 권위 게임 세션 호스트로는 쓸 수 없다. 두 용도를 섞어 보면 판단이 흐려지므로 나눠서 본다.

메타 백엔드 적합

기획서 9장은 계정·랭킹·상점을 "PlayFab 또는 UGS" 슬롯으로 비워 뒀다. Supabase가 그 자리를 더 잘 채운다 — Postgres라 리더보드·매치 히스토리를 SQL로 자유롭게 짜고, RLS로 행 단위 권한을 선언하고, Auth가 무료 50,000 MAU를 덮고, C# SDK가 공식 지원(netstandard2.1 · Unity 명시)이다.

단, 지금 그 슬롯은 범위 밖이다. 친구방은 계정·랭킹·MMR이 필요 없다 → 도입 시점은 M6(재접속 토큰이 급하면 M5).

권위 세션 호스트 부적합

Edge Functions는 Deno 런타임의 상태 없는 TypeScript/WASM 핸들러고, Supabase 자신이 단일 실행을 2초 이내로 권장한다. 30~60분짜리 매치의 손패를 메모리에 들고 있을 수 있는 물건이 아니다.

더 결정적인 건 언어다. 우리 룰 엔진은 4,300줄 순수 C#이고 10만 판 무결성 + 테스트 325개 + CI가 그 위에 걸려 있다.

여기서 타협하면 이 저장소의 중심 명제가 깨진다

Supabase에서 권위를 돌리는 길은 두 가지뿐이고, 둘 다 받아들이기 어렵다.

  • 룰 엔진을 TypeScript로 재구현 — 진실이 두 개가 된다. "하나의 룰 엔진으로 싱글과 멀티의 룰 불일치를 없앤다"는 설계 명제를 정면으로 부순다. CI의 코어↔유니티 해시 동기 검사가 지키고 있는 바로 그 불변식이다.
  • C#을 WASM으로 컴파일해 Deno에서 호출 — 기술적으로는 가능하지만 매 액션마다 전체 상태를 직렬화해 넣고 빼야 하고, 툴체인이 이국적이다. 1인 개발이 길게 감당할 유지보수가 아니다.

그래서 Supabase를 도입하더라도 전용 .NET 서버 결정은 그대로 유효하다. 오히려 궁합이 더 좋다 — Supabase Auth가 발급한 JWT를 .NET 서버가 검증하는 구성은 가장 흔한 표준 패턴이고, 권위·손패·재접속을 제대로 가져가면서 계정·랭킹을 Supabase에 맡길 수 있다.

대신 이건 진짜 새 선택지다 — Supabase가 Photon을 대체한다

Realtime에는 private: true 채널 + realtime.messages RLS 정책으로 좌석별 비공개 전달을 하는 길이 있다. 기획서가 금지한 "상대 손패를 같은 채널에 흘리기"를 피하면서 호스트 모델을 세울 수 있다는 뜻이다. 그러면 Auth·로비 테이블·릴레이가 전부 한 벤더로 모이고 운영할 서버가 없다. 호스트 이탈 결함은 그대로 남지만, 호스트 모델을 택할 거라면 Photon보다 Supabase가 낫다.

분해

한 스펙에 안 들어간다 — 여섯 조각

  1. 프로토콜 + 권위 세션 + 로컬 루프백 먼저 짓자

    메시지 DTO · 좌석별 시야 마스킹(ProjectFor) · RemoteAgent · ITichuTransport + 같은 프로세스에서 도는 루프백 구현. 네트워크 코드 0줄.

    검증: 기존 싱글플레이를 이 경로 위로 올린 뒤 같은 시드에서 기존 결과와 비트 동일 + 기존 테스트 전부 그린. 전부 dotnet에서 돌아 CI에 들어간다.

  2. 실제 전송 + 호스팅 전송 결정 필요

    ①이면 Supabase Realtime(또는 Photon) 채널, ②면 ASP.NET WebSocket 서버 + 배포. M1의 ITichuTransport 뒤에 끼우는 작업이라 게임·UI 코드는 손대지 않는다.

  3. 방 · 초대 코드 · 좌석/팀 배치 · 빈자리 AI

    코드로 방 만들고 들어오기, 팀 수동 조정, 부족한 인원은 AI로 채워 4인 보장. 기획서 6장 로비 사양을 따른다.

  4. 로비 UI · 턴 타이머 · 연결 상태 표시

    셸의 SelectFriendRoomStub 자리를 실제 화면으로 채운다. 테이블 화면은 좌석에 사람 이름과 연결 상태만 추가되면 거의 그대로 쓴다.

  5. 타임아웃 · 끊김 · 재접속 · AI 인계

    기획서 7.7 그대로: 일반 20초 / 콜·교환 30초, 만료 시 팔로우는 자동 패스 · 리드는 오토플레이, 60초 유예 후 AI 인계, 재접속은 전체 스냅샷 재전송.

  6. 계정 · 랭킹 · MMR 친구방 범위 밖

    여기가 Supabase가 들어올 자리다 — Auth · Postgres · RLS로 한 번에 덮인다. 다만 랭킹전을 할 때 비로소 필요하므로 지금 짓지 않는다.

각 조각이 자기 스펙 → 구현 계획 → TDD 구현 사이클을 갖는다. M1만 끝나도 "친구방이 돌아갈 자리"가 코드로 생기고, 그 시점까지 서버를 하나도 띄우지 않는다. 그래서 전송 결정을 M2까지 미뤄도 손실이 없다.
