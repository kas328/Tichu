# 멀티플레이 M3 — 다중 방 · 랜덤 매칭 대기열 (설계 스펙)

- **날짜:** 2026-10-08
- **트랙:** Phase 3 멀티플레이. M2b(클라우드 배포, 브랜치 `feat/mp-m2b`) 다음 증분.
- **상태:** 설계 승인됨(brainstorming). 구현 계획 수립 전.
- **기반 브랜치:** `feat/mp-m3` ← `feat/mp-m2b`(프로토콜 버전 관문 · `--host` · wss 포트 수정 포함). M2b가 AWS 대기로 막혀 있어도 M3 개발·로컬 검증은 진행한다. 클라우드 배포는 M2b와 묶어 한 번에 해도 된다.
- **상위 결정(2026-10-07):** 출시 버전에 랜덤 매칭 멀티플레이를 넣는다. 순서 = M2b 배포 → **M3 다중 방 + 매칭 대기열** → M5 이탈 처리 → 정책 재신고.

## 1. 확정된 결정

1. **입장 방식 = 랜덤 매칭만.** "온라인 대전"을 누르면 대기열에 들어가고, 서버가 사람을 모아 방에 배정한다. 초대 코드 친구방은 만들지 않는다.
2. **AI 충원 = 30초 후 자동.** 4명이 모이면 즉시, 아니면 대기열에서 가장 오래 기다린 사람이 30초를 채운 순간 그때 모인 사람(최대 4명) + 빈자리 AI로 시작한다. "AI와 바로 시작" 버튼은 두지 않는다.
3. **AI 난이도 = 서버 고정 Hard.** 대기열은 하나다. 난이도는 서버 설정(`--difficulty`, env 파일 `TICHU_GAME_ARGS`)으로만 바꾼다.
4. **목표 점수 = 1000점**(정식 규칙). 서버 설정 `--target` 으로 바꿀 수 있다.
5. **방 수 상한 + 대기 안내.** 동시에 도는 방 수를 `--max-rooms` 로 묶는다. 꽉 차면 대기열에 남겨 "서버가 붐빕니다 · 대기 순번 N" 을 보여 주고, 방이 비면 순서대로 들어간다. AI 강도를 지키는 쪽을 택했다.
6. **구조 = 한 프로세스 안의 다중 방 + 매치메이커(접근안 A).**
   - 기각 B(방마다 서버 프로세스): Caddy 라우팅·포트 관리·프로세스 수명 관리가 새로 생기고, 1GB 메모리에 .NET 프로세스 여럿은 빠듯하다.
   - 기각 C(기존 전송 클래스를 방 수만큼 복제): 대기 중인 연결도 수신 루프(끊김·취소 감지)와 대기 상태 송신이 필요해, 결국 연결 소유권을 전송 클래스 밖으로 빼야 한다 — A로 수렴한다.

### 1.1 용량에 관한 사실(설계 근거)

- AI 한 수 = `PacedPimcAgent` 가 **코어 하나로 최대 900ms**(`PimcBudget`, 벽시계 예산) 계산한다. AI 차례가 이어지는 동안 방 하나는 대략 코어 하나를 쓴다.
- 예산이 벽시계라, 방이 코어 수보다 많아지면 판이 느려지지 않고 **AI가 덜 계산해 약해진다.**
- Lightsail $7 플랜은 **버스트형 CPU**다. 오래 계속 쓰면 크레딧이 소진돼 기준 성능으로 묶인다 → 상한이 필요한 이유.
- `--max-rooms` 의 잠정 기본값은 **2**(vCPU 수). 확정은 M2b 배포 뒤 Lightsail 부하 실측 한 번으로 한다(이 스펙 범위 밖).

## 2. 서버 구조

```
WebSocket 접속(/ws?v=2) ─ 버전 관문(M2b) ─ Connection(송신 큐·수신 루프·레이트리밋·크기/JSON 검사)
                                                │ 처음엔 대기열 소속
                                                ▼
                          Matchmaker ── 대기열(FIFO) · 시계 · 방 상한
                           │  ① 4명 모임 → 즉시 방
                           │  ② 가장 오래 기다린 사람이 30초 → 모인 사람 + AI 로 방
                           │  ③ 방이 상한이면 대기 유지, Busy · 순번 안내
                           ▼
                          Room (매치 1개) ── 좌석 무작위 배정 · MatchSession · PIMC Hard
                           │  ITichuTransport 구현: SendTo(좌석) → 그 좌석의 Connection
                           └ 정상 종료/폴트 → 자기 연결만 닫고 등록 해제 → Matchmaker 가 다음 묶음 시도
```

### 2.1 구성 요소

| 단위 | 책임 | 의존 |
|---|---|---|
| `Connection` | 소켓 하나. 송신 큐 + 송신 태스크(소켓당 동시 전송 금지), 수신 루프, 레이트리밋(`TokenBucket`), 16KB·텍스트·JSON 검사. 받은 액션을 **지금 소속(대기열 또는 방)** 으로 넘긴다. | `TokenBucket`, `ProtocolJson` |
| `Matchmaker` | 대기열(FIFO), 30초 충원 판정, 방 상한, 순번·Busy 계산, `Queued` 송신 시점 결정, 방 생성 요청. **판단 로직은 순수**(시계·방 생성기 주입)로 두어 단위 테스트한다. | 시계(`Func<DateTime>` 또는 동등), 방 팩토리 |
| `Room` | 매치 하나의 수명. 좌석 무작위 배정, 빈자리 `PacedPimcAgent`(Hard), `MatchSession` 시작, `ITichuTransport` 구현(좌석→연결). 사람이 끊기면 그 방에만 `SessionFaulted` 후 세션 정지. 끝나면 자기 연결을 닫고 Matchmaker 에 반납을 알린다. | `MatchSession`, `PacedPimcAgent`, `PolicyConfig`, `PimcBudget` |
| `ServerApp` | 조립과 `/ws` 핸들러(버전 관문 → Connection 생성 → Matchmaker 에 등록). | 위 전부 |

### 2.2 기존 코드의 행방

- `WebSocketServerTransport` → `Connection`(송신·수신·검사) 과 `Room`(좌석·`ITichuTransport`) 으로 나뉜다. 지금 쓰는 내부 `Connection` 클래스를 그대로 꺼낸다.
- `MatchHost` 의 매치 수명 관리(시작·이탈 폴트 방송·종료 후 정리) → `Room`.
- 매치 세대 번호(`_generation`/`_matchIndex`) → **불필요.** 방마다 자기 연결만 알고 끝나면 사라지므로, 늦게 끝난 이전 매치 연결은 소속 자체로 새 방에 닿지 않는다.
- `SeatTable` → 방 안의 무작위 배정으로 단순해진다(접속 순서 배정·끊긴 좌석 재사용 규칙이 사라짐). 삭제 또는 축소.
- `RejectAsync`(버전 불일치 거절) · 레이트리밋 · 사칭 방지(받은 액션의 Seat 을 연결 좌석으로 덮어쓰기)는 유지한다.

### 2.3 서버 옵션

| 옵션 | 기본 | 비고 |
|---|---|---|
| `--seats` | — | **삭제.** 사람 좌석은 매치메이커가 정한다. |
| `--fill-after <초>` | 30 | AI 충원 대기. 개발·테스트에서 짧게. |
| `--max-rooms <N>` | 2 | 동시 방 상한. 실측 후 조정. |
| `--difficulty` | Hard | 기존 옵션. 기본값을 Hard 로. |
| `--target` | 1000 | 기존 옵션. |
| `--host`, `--port`, `--ai-delay`, `--seed` | 기존 | `--seed` 는 방 번호로 결정적 변주(기존 매치 번호 변주와 같은 방식). |

## 3. 프로토콜 (v1 → v2)

- `ProtocolVersion.Current = 2`. v1 앱은 M2b 관문이 "앱을 업데이트해 주세요 (서버 프로토콜 v2)" 를 보내고 닫는다.
- **새 서버 이벤트 `Queued`** — 대기 중인 연결에만 보낸다.

| 필드 | 뜻 |
|---|---|
| `Waiting` | 지금 대기열에 있는 사람 수(나 포함) |
| `FillInSeconds` | 내 묶음이 AI 충원으로 시작하기까지 남은 초. Busy 면 null |
| `Busy` | 방 상한에 걸려 대기 중인가 |
| `Position` | Busy 일 때 내 대기 순번(1부터) |

- **송신 시점:** 대기열이 바뀔 때만(입장·이탈·Busy 전환·순번 변화). 카운트다운은 클라이언트가 `FillInSeconds` 를 받은 시각부터 직접 센다. 매초 보내지 않는다.
- **방이 만들어지면:** 기존 `Lobby(내 좌석, 인원, 인원)` 를 보내고 곧바로 첫 `StateUpdate` 가 이어진다. 클라이언트의 매치 시작 판정(`LobbyWaiter.Started`) 은 지금 로직 그대로다.
- **새 클라이언트 액션 없음.** 대기 취소 = 연결 닫기. 서버는 끊긴 연결을 대기열에서 뺀다.
- 열거형은 이름 문자열 · 역직렬화 카드는 정규 카드 재생성 등 M2 직렬화 규칙은 그대로다.

## 4. 클라이언트

```
메뉴 → [온라인 대전] → 주소 화면(NetJoin, 지금 그대로) → 접속
     → 대기 오버레이: "상대를 찾는 중 · 2명 대기 · 18초 뒤 AI와 시작"
                       Busy 일 때: "서버가 붐빕니다 · 대기 순번 3"     [취소]
     → Lobby 수신 → 테이블(좌석 회전 기존) → 매치 종료 → 결과 → 메뉴
```

- **바뀜:** `LobbyWaiter` 가 `Queued` 를 먹고 문구·남은 초를 만든다(시계 주입으로 테스트). 대기 오버레이 문구. 모드 선택 화면의 "친구방" 버튼 → "온라인 대전"(라벨이 메뉴 뷰·씬에 있으면 함께).
- **그대로:** 주소 입력 화면(출시 빌드 주소 고정은 M2b 스펙대로 M4), `TichuClient`, 테이블, 좌석 회전(`SeatRotation`), 매치 후 서버가 연결을 닫는 흐름. "한 판 더" = 메뉴에서 다시 들어가기.
- **좌석:** 방 생성 때 사람 좌석을 무작위로 정한다. 사람 둘이 같은 팀일 수도, 상대일 수도 있다. 클라이언트는 이미 "나 = 아래" 로 회전하므로 화면 변경은 없다.

## 5. 오류 처리 · 동시성

| 상황 | 처리 |
|---|---|
| 대기 중 끊김·취소 | 대기열에서 빼고 남은 대기자에게 `Queued` 재송신. |
| 매치 중 사람 이탈 | **그 방만** `SessionFaulted` 후 종료(M5 전 정책 유지). 다른 방 무영향. |
| 방 종료(정상·폴트) | 그 방 연결만 닫고 등록 해제 → Matchmaker 가 대기열에서 다음 묶음 시도. |
| 동시 입장·이탈·30초 도달 | 대기열 판단(묶기·상한·순번·`Queued` 내용 결정)은 **Matchmaker 잠금 하나 안에서.** 방 시작(AI 생성·세션 시작)과 소켓 송신은 잠금 밖. M2 원칙("방 참과 시작은 원자적으로")을 따른다 — 잠금 안에서 묶인 연결은 같은 잠금 안에서 대기열을 떠나 그 방 소속이 된다. |
| 묶이는 순간 그 연결이 끊김 | 방 시작 직후 끊김과 같다 → 그 방 폴트. 잠금 안 소속 전환 덕에 대기열·방 양쪽에 동시에 있는 연결은 없다. |
| 30초 타이머 | 서버 전체 시계 하나. 1초 틱마다 가장 오래 기다린 사람만 확인. 시계 주입으로 테스트에서 시간을 직접 돌린다. |
| 레이트리밋·16KB·깨진 JSON·좌석 사칭 | 연결 계층에서 그대로(대기 중에도 적용). 대기 중 받은 게임 액션은 무시하지 않고 **연결을 닫는다**(정상 클라이언트는 보내지 않는다). |
| 서버 로그 | 방 생성(방 번호·사람 수·AI 수·seed)·방 종료(정상/폴트 사유)·Busy 전환을 남긴다. |

## 6. 테스트

dotnet `Tichu.Server.Tests`(net10). `Tichu.Net` 변경분(`ServerEvent`·`ProtocolVersion`)은 기존대로 Unity 미러와 `Tichu.Core.Tests` 에 반영한다.

- **Matchmaker 단위**(가짜 시계·가짜 연결·가짜 방 팩토리)
  - 4명 → 즉시 방 1개, 좌석 4개 모두 사람.
  - 1~3명 → 30초 전엔 방 없음, 30초에 그 인원 + AI 로 방.
  - 5명 → 방 1개(4명) + 1명 대기, 남은 1명의 30초는 **그 사람의 입장 시각** 기준.
  - 상한 도달 → Busy·순번 송신, 방 반납 시 순서대로 입장.
  - 대기 중 이탈 → 대기열에서 빠지고 `Queued` 재송신, 순번 당겨짐.
  - 좌석 무작위 배정 — 중복 없음, 여러 seed 에서 분포가 고정 좌석이 아님.
- **Room**: 한 방의 폴트가 다른 방 연결에 이벤트를 보내지 않음, 종료된 방 등록 해제·연결 닫힘.
- **E2E**(실제 WebSocket, `--fill-after` 짧게, 빠른 AI 지연)
  - 클라이언트 2개 → 같은 방, AI 2명과 짧은 목표로 완주.
  - 클라이언트 5개 → 방 2개로 갈림.
  - v1 접속 → 업데이트 안내 후 닫힘.
- **음성 대조(M2 교훈):** 핵심 가드(상한 검사, 잠금 안 소속 전환, 대기 이탈 제거, 30초 기준 시각)를 하나씩 빼면 해당 테스트만 실패하는지 확인한다.
- **Unity:** `LobbyWaiter` 가 `Queued` 로 문구·카운트다운을 만들고, 이어지는 `Lobby`+`StateUpdate` 에서 기존대로 시작 판정. Presentation 전체 회귀.

## 7. 완료 조건(DoD)

1. 위 테스트 그린 + 기존 dotnet core · server · Unity Presentation · 미러 core(클래스 필터) 회귀 없음.
2. **로컬 실기:** PC 서버 + 에디터 + S23 두 기기가 같은 방 → AI 2명과 대전. 혼자 접속하면 30초 뒤 AI 3명과 시작.
3. **상한 확인:** `--max-rooms 1` 에서 두 번째 묶음에 "붐빔·순번" 표시, 첫 방이 끝나면 자동 입장.
4. 새 APK 로 실기(밀린 수정 확인과 함께) — v1 앱은 업데이트 안내를 받는다.

## 8. 범위 밖

- 클라우드 부하 실측과 `--max-rooms` 기본값 확정 → M2b 배포 뒤 한 번.
- 턴 타이머 · 재접속 · AI 인계 → M5.
- 출시 빌드 주소 고정 · 로비 UI · 거부 메시지 표출 → M4.
- 계정 · 랭킹 · MMR → M6(출시 범위 밖이어도 됨).
- 출시 전 Data safety · 등급 · 개인정보처리방침 재신고(온라인 대전 추가).
